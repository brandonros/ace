# ace

Research and experiments for an **agent command center** built around our existing internal Claude Code workspace API.

**Status:** discovery and proof of concept. The architecture and API below are proposals, not implemented capabilities.

## What we are trying to achieve

Make our existing agent environment useful for both engineer-directed work and a small number of repeatable background workflows.

An engineer should be able to start work, leave it running, return to the right session, inspect the changes and verification results, and intervene when needed. A scheduled workflow should use the same execution capabilities and produce an accountable outcome.

The first milestone is **one repeatable task that produces a useful, reviewable result**. More concurrent agents and larger projects come after that.

## Starting point

We already have an internal API that exposes a Claude Code workspace containing skills, agents, repositories, monorepos, and development tools.

Our current workflow includes:

- A `do-my-ticket` skill that researches a Jira ticket and attempts to produce a draft PR.
- A periodic Jira scan that finds eligible tickets.
- Jira comments and statuses used to track progress.
- Filesystem-backed agent sessions identified by GUIDs.
- An existing container/workspace environment that we want to reuse.

The immediate problem is making this system understandable and reliable: what a request starts, which files and session it owns, what happens after a disconnect or restart, and how a reviewer knows what was actually verified.

We have not yet documented or validated the internal API's guarantees. An accessible workspace is not automatically an isolated workspace, a resumable job, or a verified implementation.

## Questions this project should answer

1. **Useful work:** Which recurring tasks have clear inputs, measurable acceptance criteria, and an engineer who wants the output?
2. **Interactive use:** Can someone inspect, continue, and stop work without losing the session or searching through GUID folders?
3. **Background execution:** Can scheduled work survive disconnections and recover from failures without duplicate changes?
4. **Verification:** Can we provide evidence that reduces review effort, including relevant regression, integration, performance, or partner-contract checks?
5. **Reuse:** Which lifecycle operations are common, and which instructions and checks remain specific to each task or repository?
6. **Platform scope:** What can our existing API already do, and what small additions are actually necessary?

A chat UI, a protocol adapter, a workflow engine, and a sandbox solve different parts of this problem. We should evaluate them against these questions.

## Proposed boundaries

| Layer | Responsibility | Initial approach |
| --- | --- | --- |
| Intake | Manual requests, Jira labels, scheduled triggers | Keep the existing Jira poll; add explicit request identity |
| Run coordination | State, ownership, limits, recovery, waiting for input | Small coordinator around the existing API; evaluate Temporal if needed |
| Agent execution | Claude sessions, skills, tools, code changes | Reuse the existing workspace API and Claude harness |
| Workspace | Checkout, branch, dependencies, filesystem, credentials | Document current behavior; isolate writable work before adding concurrency |
| Verification | Build/test results, CI status, evidence tied to a commit | Run explicit checks and retain their actual output |
| Operator interface | List runs, inspect evidence, continue or cancel | Start with existing surfaces; compare UI references separately |

Jira can remain the business-facing record of requests and progress. If we add a coordinator, it should own execution state and synchronize summaries to Jira, rather than infer every transition from free-text comments.

## Experiments and next steps

### 1. Inventory the existing workspace API

Document the actual endpoints and run one small task end to end. Record:

- Authentication and which user's permissions a run receives.
- How repository, working directory, skill, and agent are selected.
- Whether requests execute synchronously or return a durable run identifier.
- How session creation, continuation, history retrieval, and cancellation work.
- What survives an HTTP disconnect, process restart, or pod replacement.
- Whether concurrent runs share files, branches, credentials, or mutable configuration.
- Where logs, tool events, usage, test results, and PR links are stored.

**Deliverable:** an API capability map with observed behavior, missing operations, and one recorded example. Do not start by replacing the service.

### 2. Define a small run contract

Distinguish these concepts:

| Entity | Meaning |
| --- | --- |
| Work item | The requested outcome, such as a Jira ticket plus an explicit automation request |
| Run | One bounded attempt to produce that outcome |
| Session | Claude's conversational/execution context; a run may reference multiple sessions |
| Workspace | The checkout and filesystem where execution happens |
| Evidence | Commits, diffs, test results, CI runs, logs, and review findings |

Proposed application endpoints, only where the existing API lacks equivalents:

```http
POST /runs
GET  /runs?cursor=...
GET  /runs/{run_id}
GET  /runs/{run_id}/events?cursor=...
POST /runs/{run_id}/inputs
POST /runs/{run_id}/cancel
```

These are **our application contract**, not an industry-standard agent API. Describe them with OpenAPI if implemented.

Starting a run should accept an idempotency key, task input, repository/workspace selection, skill version, and execution limits. Repeating the same start request should return the existing run. An intentional new attempt gets a new request identity.

A run should expose its state, owner, session/workspace references, timestamps, usage, artifacts, and any actionable failure or question. Cancellation should distinguish a request to stop from confirmation that execution has stopped.

Use explicit states such as `queued`, `running`, `waiting_for_input`, `verifying`, `ready_for_review`, `failed`, and `cancelled`. A draft PR existing does not by itself mean the run is ready for review.

Events should have stable IDs and cursor pagination. Live streaming is optional; reliable history retrieval and reconnection are more important for the first experiment.

### 3. Prove one narrow workflow

Select one repository and a recurring task family. Candidate experiments:

| Candidate | Required input | Expected output |
| --- | --- | --- |
| Ticket investigation | Specific question and accessible evidence | Findings, relevant code/log references, and unresolved questions |
| Reproducible regression repair | Failing reproducer and expected behavior | Draft PR with before/after reproduction and required checks |
| Prescribed migration | Explicit migration rules and scope | Draft PR with migration-specific validation |

Use a small sample of representative past tasks to establish a baseline, then try current tasks with a named reviewer.

For code changes, the initial workflow is:

1. Read the request and check whether it is actionable.
2. Claim the work and prepare an isolated checkout.
3. Invoke the existing skill through the existing API.
4. Run the configured verification.
5. Allow a bounded repair attempt when appropriate.
6. Create or update one draft PR with evidence, or report a clear blocker.
7. Update Jira and hand off to a reviewer.

Keep human merge/release decisions in the initial experiment. Feature work is eligible when its acceptance criteria and verification are concrete; broad product decisions require clarification.

**Deliverable:** useful results on representative tasks, plus an honest account of failures and reviewer effort.

### 4. Test failure handling before increasing concurrency

Exercise a duplicate trigger, lost HTTP response, worker restart, failing test, cancellation, and a task requiring clarification.

Confirm that:

- Duplicate requests do not create duplicate active work or PRs.
- Runs have time, spend, and repair-attempt limits.
- Incomplete work is visible and recoverable.
- Agent workspaces do not overwrite each other.
- Verification refers to the exact submitted commit.
- Retrying an operation reconciles any side effects already produced.

A one-worker POC may fit in one script. Local process locking and persistent run records may suffice there. Multiple replicas need coordinated claims or a workflow engine; pod-local lock files do not coordinate separate pods.

### 5. Decide whether Temporal and a UI earn their complexity

[Temporal](https://docs.temporal.io/ai) is a candidate for durable sequencing, retries, timers, human-input waits, and coordinating multiple workers.

Evaluate it when these concerns dominate our custom code. If adopted, put external calls and agent execution in Activities, and keep the coordinating Workflow deterministic. Temporal recovery does not automatically restore the filesystem or checkpoint the inside of an opaque Claude invocation.

Evaluate a UI against concrete tasks: find a run, inspect its history and diff, see verification, answer a question, and stop execution. Background workflows should not depend on opening a chat window.

**Deliverable:** a decision based on observed gaps and operating cost. Deployment and licensing approval remain prerequisites for adopting external components.

## What to measure

- Useful outcomes accepted by the requesting engineer.
- Human review and rework time compared with the current process.
- Verification pass rate and failures found during review.
- Run cost and elapsed time.
- Duplicate-work incidents and recovery success.
- Failure categories: unclear request, missing context, environment, implementation, verification, or orchestration.

PR count, agent count, and generated lines of code are activity metrics. They do not establish value or production safety. Missing partner, performance, or cost checks remain explicit gaps even when unit tests pass.

## Protocols: choose by boundary

| Interface | Purpose | Relevance to ace |
| --- | --- | --- |
| OpenAI-compatible Chat Completions | Model-style requests, responses, and tool-call messages | Possible adapter for generic chat clients; commonly `POST /v1/chat/completions` and `GET /v1/models` |
| Anthropic-compatible Messages | Anthropic-style messages and tool-use blocks | Another client compatibility option; commonly `POST /v1/messages` |
| [Open Responses](https://www.openresponses.org/specification) | Responses-style items, tool interactions, and streaming events | Evaluate if a chosen client needs it |
| [Agent Client Protocol (ACP)](https://agentclientprotocol.com/) | Interaction between an agent and a compatible client | Relevant to sessions, tool activity, and permission interactions; see the [Claude adapter](https://github.com/agentclientprotocol/claude-agent-acp) |
| [Model Context Protocol (MCP)](https://modelcontextprotocol.io/specification/2025-11-25) | Agent access to tools and context | Relevant to Jira, internal knowledge, and operational tools |
| Our run API | Work ownership, lifecycle, history, evidence, cancellation | The contract we need to clarify around the existing service |

Application routes such as `/api/chat/completions` may proxy a provider interface; their prefixes are not universal protocol requirements.

A Claude workspace is an executing agent, not just a model endpoint. Any compatibility adapter must specify which tool calls it executes internally, which it delegates to the client, and how it represents permissions, failures, and session continuation. Returning streamed text alone does not settle those semantics.
